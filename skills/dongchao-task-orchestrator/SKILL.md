# 任务编排法

把需求文档转化为简单、清晰、可执行、可并发、可验收、不过度复杂的任务结构。先完成需求理解、边界判断和任务编排，再进入具体实现。

## 总原则

- 始终围绕最小业务闭环拆任务：用户真正要完成什么动作、最核心交付物是什么、哪些任务不做就无法交付。
- 使用第一性原理拆回目标、用户、输入、处理、输出和验收，不要先入为主套模板。
- 使用 MECE 检查任务是否不重、不漏、同层级。
- 使用概率结构关系判断任务边界：互斥、重叠、包含、依赖、不确定。
- 使用奥卡姆剃刀控制复杂度：能合并就合并，能后置就后置，禁止为了显得完整而制造任务。
- 不要直接开始生成应用、页面、数据表、自动化流程或代码；先输出任务编排结果。

## 分析顺序

严格按以下顺序执行，不要跳步：

```text
第一性原理
↓
MECE 拆解
↓
概率结构判断
↓
奥卡姆剃刀复杂度控制
↓
WorkTree 执行编排
↓
测试验收与风险控制
```

## 第一步：需求理解摘要

用 300 字以内说明：

- 业务目标是什么
- 服务哪些用户角色
- 核心业务流程是什么
- 最终要交付什么系统、应用、模块或能力
- 最小业务闭环是什么

## 第二步：第一性原理分析

输出表格：

| 问题 | 回答 |
| --- | --- |
| 用户真正要解决的问题是什么 | |
| 用户真正要完成的业务动作是什么 | |
| 最小可交付结果是什么 | |
| 最小业务闭环是什么 | |
| 哪些任务不做就无法交付 | |
| 哪些任务可以后置 | |
| 哪些任务可能是过度设计 | |

同时把需求分为四类：

| 类型 | 含义 | 判断标准 |
| --- | --- | --- |
| 核心任务 | 不做就无法完成交付 | 影响最小业务闭环 |
| 支撑任务 | 不做会影响质量、稳定性或一致性 | 支撑核心任务运行 |
| 增强任务 | 做了更好，但当前阶段不是必须 | 可放入后续版本 |
| 应删除任务 | 没有明确价值、不可验收或来自模板惯性 | 不应进入 WorkTree |

## 第三步：提取关键业务对象

从需求文档提取关键对象，不明确的内容放入待澄清。

| 类型 | 名称 | 说明 | 是否明确 | 待澄清点 |
| --- | --- | --- | --- | --- |

对象类型包括：业务目标、用户角色、业务流程、功能模块、页面、数据对象、字段、权限、自动化、消息通知、数据看板、外部集成、异常场景、验收标准。

## 第四步：生成初步任务清单

每个任务必须有明确输入、输出、层级、版本、优先级和执行建议。

| 任务编号 | 任务名称 | 任务说明 | 输入 | 输出 | 所属层级 | 版本 | 优先级 | 初步执行建议 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |

优先级定义：

| 优先级 | 含义 |
| --- | --- |
| P0 | 核心闭环任务，不做无法交付 |
| P1 | 重要支撑任务，不做会影响质量 |
| P2 | 增强任务，做了更好但可后置 |
| P3 | 可删除或暂不处理任务 |

禁止把所有任务都标成 P0。

## 第五步：MECE 校验

先校验初步任务清单。如果不通过，先修正任务结构，再继续输出 WorkTree。

| 检查项 | 判断标准 | 是否通过 | 问题说明 | 修正建议 |
| --- | --- | --- | --- | --- |
| 是否重叠 | 任务之间是否修改同一对象或表达同一需求 | | | |
| 是否遗漏 | 需求文档中的关键对象是否都被覆盖 | | | |
| 是否同层级 | 同一层任务是否处在同一抽象层级 | | | |
| 是否可执行 | 每个任务是否有输入、输出和验收标准 | | | |
| 是否可并发 | 并发任务之间是否没有依赖和冲突 | | | |
| 是否有待澄清项 | 信息不足处是否被明确列出 | | | |

## 第六步：任务关系诊断

关系类型只能使用：互斥、重叠、包含、依赖、不确定。

| 任务 A | 任务 B | 关系类型 | 判断理由 | 是否可并发 | 执行建议 | 风险 |
| --- | --- | --- | --- | --- | --- | --- |

判断规则：

- 互斥：目标、输入、输出和修改对象不同，结果互不影响，可并发。
- 重叠：涉及同一页面、数据对象、字段、流程节点、权限或同一需求表达，暂不并发；先抽公共前置任务。
- 包含：一个任务是另一个任务的一部分，不能放在同一层级；先定义父任务边界。
- 依赖：后置任务必须使用前置任务结果，必须串行。
- 不确定：信息不足，不要猜测，列入待澄清。

## 第七步：复杂度刹车检查

在输出最终 WorkTree 前进行复杂度检查。如果不通过，先简化。

| 检查项 | 判断标准 | 是否通过 | 问题说明 | 修正建议 |
| --- | --- | --- | --- | --- |
| 是否过度拆分 | 是否存在无法独立验收的小任务 | | | |
| 是否过度并发 | 是否为了并发而拆分任务 | | | |
| 是否过度设计 | 是否加入当前需求未要求的功能 | | | |
| 是否模板化套用 | 是否照搬通用系统结构而非来自需求文档 | | | |
| 是否可以合并 | 是否存在可以合并且不增加风险的任务 | | | |
| 是否有最小闭环 | V1 是否能完成核心业务流程 | | | |
| 是否区分版本 | 是否区分 V1 必做、V2 增强、V3 优化 | | | |

## 第八步：生成 WorkTree 任务结构

按以下层级输出：

```text
L0：项目目标与边界确认
├── 任务 0.1：
├── 任务 0.2：

L1：公共前置任务
├── 任务 1.1：
├── 任务 1.2：

L2：核心数据、流程与权限设计
├── 任务 2.1：
├── 任务 2.2：

L3：模块级任务拆分
├── 模块 A：
│   ├── 任务 A1：
│   ├── 任务 A2：
├── 模块 B：
│   ├── 任务 B1：
│   ├── 任务 B2：

L4：可并发执行任务
├── 并发组 1：
│   ├── 任务：
│   ├── 任务：
├── 并发组 2：
│   ├── 任务：
│   ├── 任务：

L5：集成联调任务
├── 任务 5.1：
├── 任务 5.2：

L6：测试、验收与优化任务
├── 任务 6.1：
├── 任务 6.2：
```

L4 只放真正可并发执行的任务。并发任务必须无共享修改对象、无前后依赖、无输出覆盖风险。

## 第九步：输出任务节点执行说明

为每个任务节点输出：

| 任务编号 | 任务名称 | 输入 | 输出 | 前置依赖 | 是否可并发 | 并发组 | 版本 | 优先级 | 风险 | 验收标准 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |

要求：输入具体、输出可交付、前置依赖明确、风险具体、验收标准可判断。

## 第十步：输出待澄清问题

| 问题 | 影响范围 | 为什么必须澄清 | 建议提问方式 |
| --- | --- | --- | --- |

如果没有关键缺口，明确写：

```text
当前需求文档中未发现影响任务拆分的关键缺口。
```

## 最终输出结构

严格按以下结构输出：

1. 需求理解摘要
2. 第一性原理分析
3. 关键业务对象表
4. 初步任务清单
5. MECE 校验表
6. 任务关系诊断表
7. 复杂度刹车检查表
8. WorkTree 任务结构
9. 任务节点执行说明表
10. 待澄清问题
11. 执行建议总结

## 强制要求

- 不要直接生成应用、页面、数据表、自动化流程或代码。
- 不要把父任务和子任务放在同一层级。
- 不要把存在重叠关系的任务放入同一个并发组。
- 不要把原因、结果、功能、页面、数据对象混在同一层级。
- 不要为了显得完整而拆出过多虚假任务。
- 不要为了并发而并发。
- 不要照搬通用模板，所有任务必须来自需求文档或交付所必需的隐性基础任务。
- 不要输出空泛建议，所有任务必须有输入、输出和验收标准。
- 如果需求文档信息不足，明确指出，不要编造。
- 如果任务关系不确定，标记为“不确定”，并列入待澄清问题。
- V1 必须优先保证最小业务闭环，不得塞入非必要增强功能。
- 如果任务无法独立执行、无法独立验收、没有明确输出，应合并、后置或删除。
