# 多维表格业务设计方法论

**核心原则：先问清楚，再动手搭。** 不要拿到需求就直接建表，先用六个问题把业务翻译成结构，再用三个维度切入设计。

---

## 第一步：六个问题（搭表前必须回答）

拿到任何多维表格搭建需求，必须先搞清楚这六个问题。缺一个都不能动手。

### 1. 你要管什么业务？目标是什么？

先搞清楚这个多维表格是为哪个业务服务的，核心目标是什么。

- 目标不同，表结构完全不同
- 例：管客户跟进 vs 管项目进度 vs 管库存进出——三个目标，三种完全不同的表结构
- **输出：一句话描述业务目标**

### 2. 谁会用这个系统？角色分别是什么？

明确使用者是谁，不同角色看到的内容不同、权限不同、操作不同。

- 录入的人：需要表单、移动端友好
- 审核的人：需要审批流、状态变更权限
- 看数据的人：需要仪表盘、只读权限
- **输出：角色清单 + 每个角色的操作权限**

### 3. 数据从哪来？经过什么处理？流向哪去？

画清楚数据的完整流转路径。

- 谁录入（数据入口）
- 怎么处理（AI 字段、公式、工作流）
- 呈现给谁（数据出口）
- **输出：数据流程图或流转路径文字描述**

这决定了你需要几张表、表之间怎么关联。

### 4. 数据之间有没有关联？

识别数据之间的对应关系。

- 一对多：一个客户 → 多个跟进记录
- 多对多：多个员工 ←→ 多个项目
- 多对一：多个订单 → 一个产品
- **输出：关联关系清单**

关联关系决定了「关联字段」怎么建、「查找引用」怎么配。**先想关联，再搭表。**

### 5. 哪些数据是核心的、不可或缺的？

每张表只留 2-3 个核心字段，先把这些定下来，再慢慢扩展。

- 一上来就堆几十列，只会让系统变得没人用
- 核心字段 = 拿掉这列，这张表就失去意义的字段
- **输出：每张表的核心字段清单（≤3 个）**

### 6. 做完之后，你想看到什么、产出什么？

想清楚最终的产出。

- 仪表盘上的几个图表？（关键指标监控）
- 自动推送的提醒？（流程节点触发）
- 定期生成的报告？（数据汇总）
- **输出：预期产出物清单**

产出决定了仪表盘搭什么、自动化怎么设。

---

## 第二步：从六问到三维度的转换逻辑

六个问题不是分开回答就完了——它们的输出是三个维度的输入。按这个逻辑转换：

```
问题3（数据流程） ──────────→ 维度一（数据流程）
                                  │ 提炼出节点数 = 表数
                                  │ 提炼出箭头数 = 关联关系
                                  ▼
问题4（关联）+ 问题5（核心字段）→ 维度二（关键字段）
                                  │ 每个节点的核心字段
                                  │ 关联字段的类型和方向
                                  ▼
问题1（目标）+ 问题6（产出） ──→ 维度三（关键指标）
                                  │ 仪表盘图表
                                  │ 自动化触发器
```

**转换规则：**
- 问题3的「数据流程图」直接就是维度一的输入——每个节点就是一张表，每个箭头就是一个关联字段
- 问题4的回答决定关联字段的 type 和方向；问题5的回答决定每张表先建哪些字段
- 问题1的目标 + 问题6的产出，组合推导出需要监控什么指标、搭什么仪表盘
- 问题2的角色清单在最后配权限时用，不影响结构设计

---

## 第三步：三个维度（设计表结构）

### 📐 维度一：数据流程 → 定表定关联

从问题3的数据流程里明确每张表的定位和表间关系。

- 画数据从产生到结束的完整流转路径
- 明确每个节点：谁负责、产出什么数据
- 一个节点 ≈ 一张表
- 节点间的箭头 ≈ 关联字段
- **先画流程，再定表**

### 🔑 维度二：关键字段 → 定字段定类型

从问题4+5的答案里提炼每张表的核心字段。

- 每张表只定 2-3 个核心字段，先跑通
- 问题4的关联关系 → 确定关联字段（type: 13）的方向和目标表
- 关联字段必须在核心字段中优先建——没有关联，查找引用、汇总都无从谈起
- 扩展字段在核心字段跑通后再加

### 📊 维度三：关键指标 → 定仪表盘定自动化

从问题1+6的答案里提炼要呈现的指标。

- 指标决定了仪表盘要搭什么图表
- 指标决定了自动化要推什么消息
- 指标决定了筛选和分组怎么设

## 第三步：设计到 API 的映射（落地清单）

六个问题回答完、三个维度想清楚后，用这张表把设计答案翻译成具体的飞书多维表格 API 调用。

### 表结构映射

| 设计概念 | API 对应 | 参数示例 |
|---------|----------|----------|
| 一个节点 ≈ 一张表 | `feishu_bitable_app_table create` | `{name: "客户表"}` |
| 核心字段 | `feishu_bitable_app_table_field create` | `{field_name: "客户名", type: 1}` |
| 一对多关联 | 双方各建一个关联字段（type: 13），在「一」的一方建字段时 target_table_id 指向「多」的表 | 客户表 ↔ 跟进记录表 |
| 多对多关联 | 同上，关联字段自动处理中间关系 | 员工表 ←→ 项目表 |
| 查找引用 | 创建关联字段后，再创建 type: 18 的查找引用字段，需要关联字段 ID + 目标字段 ID | 跟进记录中引用客户名字段 |

### 字段类型速查

| 数据特征 | 推荐字段类型 | type 值 | property 配置 |
|---------|-------------|--------|---------------|
| 文本描述 | 文本 | 1 | `{}` |
| 数字/金额 | 数字 | 2 | `{formatter: "0.00"}` |
| 状态分类（少选项） | 单选 | 3 | `{options: [{name: "待处理"}, {name: "已完成"}]}` |
| 多标签 | 多选 | 4 | `{options: [{name: "标签A"}, {name: "标签B"}]}` |
| 日期/时间 | 日期 | 5 | `{date_format: "yyyy/MM/dd"}` |
| 是否型 | 复选框 | 7 | `{}` |
| 负责人 | 人员 | 11 | `{}` |
| 外部链接 | 超链接 | 15 | ⚠️ 必须省略 property 参数 |
| 附件/图片 | 附件 | 17 | `{}` |
| 自动记录 | 创建时间/修改时间 | 1001/1002 | `{}` |
| **关联另一张表** | **双向关联** | **13** | `{table_id: "目标表ID", related_field_id: ""}` |
| **从关联表取值** | **查找引用** | **18** | `{table_id: "关联表ID", link_field_id: "关联字段ID", target_field_id: "要引用的字段ID"}` |
| 聚合计算 | 公式 | 20 | `{formula: "{单价}*{数量}"}` |

**⚠️ 关键区别：** 关联字段（type: 13）建关系，查找引用字段（type: 18）从关系中取值。两者是独立的不同字段类型，不要混淆。查找引用必须在关联字段已存在之后才能创建，且需要关联字段的 ID。

### 关联 vs 查找引用 vs 公式 vs 汇总：怎么选？

| 场景 | 用什么 | 为什么 |
|------|--------|--------|
| A 表需要跳转到 B 表的记录 | 关联字段 | 建立表间关系，是骨架 |
| A 表想显示 B 表的某个字段值 | 查找引用 | 不存冗余数据，实时同步 |
| 同表内根据其他字段算值 | 公式字段 | 纯计算，如 总价=单价×数量 |
| 对关联表的数据做统计 | 汇总字段 | 如：客户表汇总所有订单总金额 |
| 想把 B 表字段复制到 A 表 | ❌ 不要这么做 | 用查找引用，别手动复制 |

**⚠️ 循环引用：** 关联字段不支持 A→B→A 的循环。遇到时：拆成中间表（如「参与记录」表连接员工和项目），或只建单向关联。

### 端到端 API 调用序列（客户跟进系统示例）

**场景：** 客户（一）← 跟进记录（多）的系统。核心字段：客户名 + 跟进内容 + 跟进日期。

```
步骤1: 创建多维表格
  feishu_bitable_app create → 返回 app_token

步骤2: 创建「客户表」
  feishu_bitable_app_table create
    {app_token, table: {name: "客户表"}}
  → 返回 table_id: "tbl_customer"

步骤3: 创建「跟进记录表」
  feishu_bitable_app_table create
    {app_token, table: {name: "跟进记录表"}}
  → 返回 table_id: "tbl_followup"

步骤4: 先给客户表建核心字段
  feishu_bitable_app_table_field create
    {app_token, table_id: "tbl_customer", field_name: "客户名", type: 1}
  feishu_bitable_app_table_field create
    {app_token, table_id: "tbl_customer", field_name: "负责人", type: 11}

步骤5: 给跟进记录表建核心字段
  feishu_bitable_app_table_field create
    {app_token, table_id: "tbl_followup", field_name: "跟进内容", type: 1}
  feishu_bitable_app_table_field create
    {app_token, table_id: "tbl_followup", field_name: "跟进日期", type: 5}

步骤6: ⚠️ 关键步骤——两表都已存在后，才能建关联字段
  feishu_bitable_app_table_field create
    {app_token, table_id: "tbl_followup",
     field_name: "关联客户", type: 13,
     property: {table_id: "tbl_customer"}}
  → 返回 field_id: "fld_link"

步骤7: 关联字段建好后，才能建查找引用
  feishu_bitable_app_table_field create
    {app_token, table_id: "tbl_followup",
     field_name: "客户名称", type: 18,
     property: {
       table_id: "tbl_customer",
       link_field_id: "fld_link",
       target_field_id: "fld_customer_name"
     }}
```

**⚠️ 创建顺序铁律：** app → 所有表 → 所有核心字段 → 关联字段（需目标表已存在）→ 查找引用（需关联字段已存在）。逆序操作必失败。

## 第四步：边界与降级

### 用户答不出六个问题时

- 答不出「数据关联」→ 先建单表跑通，后续再加关联
- 答不出「角色权限」→ 默认所有人可编辑，上线后根据反馈收权
- 答不出「最终产出」→ 先不加仪表盘，让用户用了再说
- **核心原则：能答 3 个以上就动手，边跑边补。不要因为答不全就卡住。**

### 多对多需要中间表时

多对多关系（如：员工 ←→ 项目）在飞书多维表格中通过关联字段自动处理——建一个双向关联字段即可，不需要手动创建中间表。但如果中间表本身有额外属性（如「参与角色」「投入比例」），则需要手动创建中间表：
- 中间表包含：关联员工字段 + 关联项目字段 + 额外属性字段
- 两个主表各关联到中间表

### 飞书多维表格的硬限制

| 限制项 | 上限 | 设计影响 |
|--------|------|----------|
| 单表字段数 | 200 | 核心字段 ≤3，扩展慢慢加 |
| 单表记录数 | 50,000 | 数据量大时考虑分表或归档 |
| 关联字段深度 | 不支持跨3表以上链式查找 | 设计时控制关联层级 |
| 公式字段 | 不支持跨表引用 | 跨表计算用查找引用+公式组合 |

## 第五步：执行顺序

```
六个问题 → 三个维度 → 设计到API映射 → 动手搭建
    │            │              │              │
    ▼            ▼              ▼              ▼
 回答完6个    设计表结构     确定字段类型     创建多维表格
 问题再往下   定字段关联     配关联/查找      写字段配权限
  走          想指标产出     查循环引用       加数据设流程
```

**禁止：** 跳过六个问题直接建表。一上来就建表，大概率要推倒重来。

---

## 反模式（不要这样做）

| 反模式 | 为什么不行 |
|--------|-----------|
| 拿到需求直接建表 | 没想清楚业务，字段越加越多，最终没人用 |
| 一张表搞定所有事 | 没有拆表，数据冗余，维护困难 |
| 先堆字段再想关联 | 关联关系是骨架，字段是血肉，骨架没定就填肉，结构一定乱 |
| 照着别人的模板直接抄 | 模板是结果不是过程，你的业务流程和别人不同 |
| 忽略角色权限 | 录入的人看到不该看的、审核的人没有操作权限，系统直接废掉 |

## 快速检查清单

搭表前逐项确认：

- [ ] 能用一句话说清业务目标
- [ ] 列出了所有角色和各自的操作权限
- [ ] 画出了数据流转路径（入口→处理→出口）
- [ ] 明确了表间的关联关系（一对多/多对多）
- [ ] 每张表的核心字段不超过 3 个
- [ ] 说得清最终要产出什么（仪表盘/提醒/报告）

全部 ✅ 才能动手建表。
