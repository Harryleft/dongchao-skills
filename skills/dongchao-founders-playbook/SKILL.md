## 核心理念

AI最危险的，不是它会犯错，而是它会用同样的热情帮你把烂想法做成产品级。

**创始人的角色转变：** 从「个人贡献者」变为「AI代理编排者」——把注意力放在更高维度的工作上：生成想法、指挥系统（AI代理、工具、小团队）来执行。

**核心原则：** 在所有阶段，把 Claude 当魔鬼代言人是核心用法。

---

## 产品矩阵：选哪个 Claude 工具

| 任务类型 | 用哪个 | 为什么 |
|---------|-------|-------|
| 快速问答、改写、头脑风暴 | Chat | 快，对话式，无需设置 |
| 研究、分析、从文件和系统中产出文档 | Claude Cowork | 文件夹访问、连接器、技能、定时运行 |
| 写代码、测试、交付软件 | Claude Code | 代码库访问、diff、git、开发环境 |

三者底层是同一个 Claude，区别在于工作空间。

## 一、Idea 阶段

### 目标
研究导向的验证：在投入资源构建之前，收集可靠证据证明问题真实存在，且你的方案有效解决了它。

### 退出条件（全部满足才能进入MVP）
1. **问题是真实且具体的吗？** 能说出谁遇到、多频繁、多严重、现在怎么解决的
2. **你的方案解决的是实际的问题吗？** 不是最初假设的问题，而是验证过程揭示的
3. **有足够信号支撑开始构建吗？** 永远不可能有100%确定性，但有足够的定性证据

### 失败模式

| 模式 | 描述 | 后果 |
|------|------|------|
| **把构建当验证** | AI让"有想法→做原型"的路径极其容易，但原型≠验证 | 42%的创业失败是因为做了没人要的东西，这个比例还会上升 |
| **过早扩展** | 构建太容易，容易在验证之前就扩展执行规模 | 对一个根本错误的假设生成整个代码库 |
| **失去客观性** | 向AI要支持你已有信念的证据，它一定能找到 | 确认偏误被AI工具大幅增强 |

### 关键练习

**1. 用结构化对抗思维压力测试问题假设：**
> Claude，反驳我的想法。找出推翻我假设的否定性证据。

**2. 磨炼问题陈述：**
> "合同审查太慢" → 不可测试
> "中型公司法务团队每次合同审查需要3天以上，因为修改意见在邮件线程中管理而非单一版本控制文档" → 可测试

**3. 客户发现——三问原则：**
- 谁（精确画像：职位、公司类型、团队结构、职级）
- 问什么（问过去做了什么，不问将来会做什么）
- 怎么分析（每次5个访谈后，让AI输出支持假设的证据VS挑战假设的证据）

**4. 竞争格局地图（分层）：**
- 直接竞争对手
- 间接竞争对手
- 潜在收购方
- 可能进入你领域的相邻玩家

**5. TAM/SAM/SOM 模型：** 用公开数据构建，压力测试背后的假设。

**6. 用Claude Code构建轻量原型：** 只建核心交互，给5个目标用户试用。

## 二、MVP 阶段

### 目标
- 把已验证的问题转化为真实用户愿意使用的产品
- 快速迭代但不积累会复合的技术债务
- 从第一天起建立持久上下文（CLAUDE.md）

### 退出条件（产品-市场匹配的真实证据）
1. **留存** — 用户不断回来
2. **收入** — 用户愿意付费  
3. **推荐** — 用户告诉别人

### 失败模式

| 模式 | 描述 |
|------|------|
| **Agentic技术债务** | 没有规范和架构约束，每次会话重新推导基础决策，代码库缺乏连贯的心智模型 |
| **虚假PMF** | 早期动能（创始人朋友、投资人资源、Hacker News热点）≠ 产品-市场匹配 |
| **零摩擦范围蔓延** | 每个功能只花一个下午就能加，但产品逐渐偏离方向 |
| **经验不足的安全漏洞** | AI生成功能代码但不生成安全代码，漏洞直到被利用才显现 |

### 关键练习

**1. 构建前定义架构和范围：**
- 创建 CLAUDE.md：架构原则、要避免的依赖、接受的取舍
- 创建范围文档：产品做什么、**明确不做什么**、功能修订标准

**2. Claude Code工作流模板：**
```
每次会话开始：回顾范围文档 + CLAUDE.md
每次会话结束：更新CLAUDE.md + 记录做了什么、决策了什么、引入了什么假设
```

**3. 上市前安全审查：** 审查认证与会话处理、API响应数据暴露、输入验证和注入风险、已知漏洞依赖。

**4. 建立测量框架：**
- 用户在时：`"如果你不能再使用这个产品，你会有什么感觉？"` > 40%答"非常失望" → 有意义的PMF指标
- 设定留存基准、激活标准、Day7/Day30目标

**5. 诊断路线（3个迭代周期后未见PMF）：**
1. 是否有细分群体反应不同？
2. 设计与体验之间的差距是定位问题还是产品问题？
3. 当前产品要找到真正PMF需要什么条件？是否现实？

## 三、Launch 阶段

### 目标
- 把早期动能变成可重复、可持续的增长引擎
- 从创始人中心的运营模式转向系统化运营
- 硬化和合规化基础设施

### 退出条件
1. 增长可重复且渠道驱动（知道CAC、LTV、回本周期）
2. 产品能承受生产环境压力
3. 运营不依赖创始人个人

### 失败模式

| 模式 | 描述 |
|------|------|
| **技术债务到期** | MVP时的快捷方式在生产流量和新功能面前暴露问题 |
| **创始人成为瓶颈** | MVP时创始人参与每件事是资产，Launch时变成约束 |
| **安全合规不能再推迟** | 真实用户、真实数据、企业合同让安全从理论风险变成实际暴露 |
| **过早扩展** | 在PMF尚不稳固时进入新市场 |

### 关键练习

**1. 技术债务修复：**
- Claude Code跑全量架构审计 → 列出结构性弱点、测试覆盖缺口、重构候选
- Claude对输出排期：哪些必须在下个版本前修复，哪些可以等

**2. 创始人注意力审计：**
- Claude Cowork审计当前运营负载：每件重复性事务、每个决策、每个只因为创始人记得才运行的流程
- 分类：可完全自动化 / 需要人但不是创始人 / 需要创始人判断

**3. 构建运营系统：**
- 定义冲刺节奏、最低规格模板、Bug分类决策树、周度指标简报

**4. 构建GTM能力：** 市场细分、信息架构、分析师关系策略、销售手册

## 四、Scale 阶段

### 目标
- 从数千用户到数百万、从一个市场到多个市场
- 建立可防御的护城河（积累深度）
- 从创始人执行者转型为面向公众的高管

### 退出条件
不再是一个里程碑，而是一个阈值事件：**公司可持续，即使创始人越来越不直接运营。**

三种形态：可持续盈利 / IPO就绪 / 被收购

### 失败模式

| 模式 | 描述 |
|------|------|
| **运营层未真正委托** | Scale阶段的系统不能靠人 babysit，创始人必须学会信任 |
| **技术运营未企业级化** | 客户不仅评估你的产品，还评估你的组织能否做可靠的基础设施伙伴 |
| **组织功能缺失** | 无论团队多小，都需要财务报告、合规监控、合同管理等 |
| **GTM能力不足** | 有机增长有天花板，需要专门增长引擎 |

### 关键练习

**1. 瓶颈地图：**
- 列出当前经过你的每个工作流、决策、审批
- 问：如果你一周不在，哪些工作流会停滞？

**2. 护城河构建：**
- 整理CI/CD沉淀的用户行为数据 → 不可复制的竞争优势
- 识别一个通用竞品会搞错的领域边界情况 → 构建专门测试用例
- 映射前十客户的工作流集成深度 → 计算切换成本

**3. GTM基础设施搭建：**
- 目标客户需求文档、SLA、支持手册 → Claude Cowork 编纂和维护
- 交互式演示环境、API文档 → Claude Code 构建
- 出站序列、内容管道 → Claude Cowork 执行

## 贯穿所有阶段：魔鬼代言人模式

每次面临关键决策时：

| 场景 | 让AI扮演的角色 |
|------|---------------|
| 提出需求/写代码前 | "像苏格拉底一样追问，帮我完善需求" |
| 技术方案出来后 | "极不友好、不给情绪价值的 Code Review" |
| 纠结要不要做 | "刚听完竞品路演的、对你有偏见的投资人" |
| 看好某个市场要杀入 | "列出过去5年这个赛道死掉的产品，我现在哪点跟它们当年最像" |
| 重大个人决定 | "5年后后悔了的我，写一封信，不许安慰" |

## FDE场景映射

| 创业阶段 | 对应FDE场景 | 关键动作 |
|---------|------------|---------|
| Idea | 客户调研、三方对齐会 | 用"现状-痛点-期望"三连问验证AI场景假设 |
| MVP | AI场景落地规划书（3个首期场景） | 最小可验证的AI解决方案组合 |
| Launch | 客户试点/首个场景交付 | 建立运营流程，确保客户留存 |
| Scale | 从1个场景扩展到更多 + 案例沉淀 | 积累行业know-how和数据飞轮 |
