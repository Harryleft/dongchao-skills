# 多维表格服务地址型插件交付

把插件需求交付成业务用户可以在 Base 内打开并完成核心动作的服务地址型自定义插件。能用原生 Base 能力简单解决时，先给出原生方案；如果用户是在练习插件开发或明确要求自定义交互，说明原生替代方案后继续插件路线。

## 适用边界

仅在同时满足以下条件时使用：

- 用户明确要开发、改造、验证或部署多维表格自定义插件。
- 交付物是一个通过服务地址加载、在 Base 插件面板中运行的网页界面。

不要用于：

- 普通 Base 建表、字段、记录、视图、公式、仪表盘或工作流操作。
- 只读咨询、SKILL 审阅或仅生成 `/goal`。
- 独立 OpenAPI 服务、妙搭应用或不在 Base 插件面板中运行的普通网页。

## 核心原则

- 先判断业务动作和原生能力，不为了使用插件而开发插件。
- 默认第一版只做一个可验证的核心闭环。
- mock 只用于早期逻辑测试；涉及 Base 数据时，最终使用隔离测试 Base 验证。
- 本地可用不等于已上线；线上页面能打开也不等于插件核心流程可用。
- 测试 Base 写入、线上部署和生产数据写入使用不同授权门，不相互替代。
- 不把 token、cookie、私钥、access token 或带凭证 URL 写入项目和交付证据。

## 先读和路由

1. 读取工作区 `AGENTS.md`、用户需求、现有插件目录、`package.json`、构建脚本和部署约定。
2. 查阅当次适用的飞书自定义插件与 Base SDK 官方规范，不沿用未经验证的旧参数或域名规则。
3. 涉及 Base 创建、字段或记录读写时，读取当前环境的 `lark-base` 规则和对应写入 reference。
4. 优先复用已有插件结构；新插件默认放入工作区约定的 `base-plugins/<plugin-name>`。
5. 实现前完成部署资源预检，明确本轮是仅本地交付还是包含上线，并收集必要的非敏感资源信息。
6. 新建插件、范围不清、多阶段交付、写回或部署任务，先形成包含目标、验证、边界和暂停条件的执行契约；环境提供 `qiaomu-goal-meta-skill` 时可用它生成 `/goal`。单点修复或只读诊断不强制生成完整 `/goal`。

## 部署资源预检

不要默认使用 SKILL 作者的服务器、域名、账号、目录或网络配置。执行需求实现前，先引导用户补充本轮所需资源：

- 交付范围：仅本地验证，还是包含测试环境或正式上线。
- 服务器资源：云厂商或环境类型、可用的 SSH 别名或登录方式、允许写入的新目录、可用运行时或静态托管方式、端口约束、反向代理/Tunnel/service 管理方式、禁止影响的已有服务。
- 域名资源：可用域名或目标路径、DNS 管理方式、HTTPS 终止方式、是否允许新增解析或路由、现有 CDN/代理情况。
- 发布要求：测试或生产环境、访问范围、可用性要求和回滚入口。
- 凭证状态：只确认“已在本机配置/尚未配置”，不要要求用户在对话中粘贴密码、私钥、token、cookie 或带凭证 URL。

用户不要求部署时，将服务器和域名资源标记为“不适用”，不要为了未来可能上线而阻塞本地实现。用户要求部署但资源不完整时，列出最小缺口，让用户明确选择“本轮仅本地交付”或补齐资源后再继续；不要擅自借用作者资源。

资源预检只用于选择可行架构，不等于用户已经授权外部变更。获得资源信息后，仍须通过下面的部署授权门。若用户提供了可用入口，先做只读的连通性和现状检查，再决定部署拓扑。

## 授权门

### A. 隔离测试 Base

创建真实测试 Base 或写入测试数据前，先列出 Base 名称、表、字段、样例记录数量和用途，并获得一次明确确认。用户已经明确授权创建隔离测试 Base，且上述范围已具体化时，不要对同一范围内的每批测试数据重复确认。

测试数据只能写入本次新建或用户明确指定的沙盒 Base。不要把“测试”当作修改现有业务 Base 的默认许可。

### B. 线上部署

只有用户明确要求部署或上线，并确认服务器、目录、域名或路径以及影响范围后，才进入部署阶段。用户只要求开发、修复或本地测试时，以本地验证完成作为本轮结束条件。

新增 Nginx 配置、reload、Cloudflare Tunnel、DNS 或 systemd 都属于外部变更。执行前列出变更文件、运行态影响和回滚方式；不要因为使用独立目录就假设没有影响。

### C. 现有或生产 Base 写入

执行前再次单独确认目标 Base、表、视图、记录范围、字段和预计修改数量。先回读当前值，再写入，再回读验证。删除、覆盖、批量修改或权限变更必须说明影响范围，不复用测试 Base 或部署确认。

## 交付流程

### 1. 判断业务目的

明确用户要完成的动作、当前痛点、使用角色和结果形式。检查视图、筛选、公式、lookup、自动化、仪表盘或表单能否以更低成本解决。

### 2. 收敛第一版

只保留一个端到端闭环，例如：

- 查找替换：普通文本、视图范围、命中预览、确认写回、回读。
- 重复检测：选择比较字段、归一化、结果预览、写入标记字段、回读。
- 跨表导出：选择主表和关联表、生成预览、下载 CSV/XLSX、实际打开验证。

正则、跨租户、多级权限、审计、付费和市场发布默认不进入第一版。

### 3. 设计测试夹具

按插件业务规则设计最小测试数据，不套用固定模板。所有读写插件至少覆盖正常结果、无结果、边界值和不应修改的数据。

条件化补充：

- 视图范围操作：覆盖视图内和视图外记录。
- 批量写回：覆盖目标字段、只读字段、非目标字段和批次边界。
- 去重或匹配：覆盖命中、非命中、空值、大小写和前后空格。
- 跨表导出：覆盖一对多、主表无匹配、孤儿记录和共同字段。

### 4. 本地实现

1. 先实现纯逻辑，并用最小自动化测试证明匹配、范围、转换、导出或 patch 生成正确。
2. 再接 Base SDK 适配层，读取真实表、字段、视图和记录 ID，不猜名称或 ID。
3. 再实现选择范围、输入、预览、确认、结果状态和错误恢复界面。
4. 最后处理构建、相对资源路径、服务地址前缀和可选健康检查。

插件首屏直接呈现核心操作，不做营销页。保留完成任务所需的字段说明、危险操作提示、空状态和错误信息。

### 5. 本地验证

运行项目已有的最小相关检查、核心逻辑测试和生产构建。启动本地页面后，用当前可用的浏览器控制工具或 Playwright 验证：

```text
打开插件页面
-> 读取测试 Base 上下文
-> 选择范围或输入条件
-> 预览结果
-> 执行核心动作
-> 展示结果或写回状态
-> 必要时回读 Base
```

检查控制台错误、加载状态、按钮状态、空结果、失败恢复和适用视口。只有官方明确支持移动端时，才把移动视口作为硬验收项。

### 6. 可选部署

通过部署授权门后：

1. 构建生产产物。
2. 上传到新的独立目录。
3. 按已确认方案配置 HTTPS 域名或路径。
4. 确认静态资源、下载链接和 API 请求在最终前缀下可用。
5. 如项目已有健康检查路径，复用同一路径；不要在 `/health` 与 `/healthz` 之间硬编码切换。
6. 对下载或动态结果按需要设置 `cache-control: no-store`。

### 7. 线上验证

验证最终服务地址可加载、JS/CSS 无 404、核心按钮有效，并在真实 Base 自定义插件入口中走通核心流程。检查当次官方规范要求的 iframe、CSP、合法域名和网络请求限制。

涉及下载时打开真实文件；涉及写回时证明目标范围已修改、范围外未修改、非目标字段未误改。

## 身份与权限

- 操作用户资源时默认使用用户身份；应用身份只有在用户明确要求或当前规则明确允许时使用。
- 权限不足时遵循 `lark-base` / `lark-shared` 的身份和授权恢复规则，不为绕过权限盲目切换身份。
- 遇到 `91403` 或明确不可访问错误时停止循环重试，报告缺失权限和最小恢复动作。

## 失败策略

- 同一错误连续失败两次后，必须改变方法或补充新证据，例如读取日志、控制台、官方规范或缩小最小复现。
- 没有新证据、需要新的授权或依赖外部状态变化时暂停。
- 不用机械轮次掩盖仍可推进的问题；也不在无新信息时重复相同操作。

## 完成证据

所有任务共同提供：

- 本地路径和核心业务动作。
- 执行过的测试、构建及结果。
- 真实运行环境中的交互证据。
- 已知限制、未做范围和仍需确认的动作。

按任务范围补充：

| 场景 | 必要证据 |
| --- | --- |
| 本地开发或修复 | 本地 URL、测试结果、浏览器截图或日志 |
| 真实 Base 读写 | 测试 Base URL、表/视图/样例范围、写前与写后回读 |
| 文件导出 | 下载链接、文件存在且可实际打开 |
| 线上部署 | 最终 HTTPS 服务地址、部署目录、健康检查或静态探针、线上交互证据 |
| 生产写回 | 用户确认范围、修改数量、范围外未修改证明和回读结论 |

不适用的证据标记为“不适用”，不要制造虚假缺失；因权限、网络或用户未授权而无法获得时，标记“阻塞”并给出最小替代证据。

## 暂停条件

遇到以下情况暂停：

- 需要新的登录、验证码、OAuth、应用权限或账号操作。
- 需要保存、展示或写入敏感凭证。
- 未通过对应授权门的测试 Base 写入、线上部署或现有/生产 Base 修改。
- 需要付费服务、公开发布、所有权转移或权限开放。
- 外部服务变更的影响范围或回滚方式不清楚。
- 官方规范不可访问，且会影响安全、域名、iframe、CSP、权限或发布判断。

一句话标准：在用户授权的范围内，业务用户能从 Base 自定义插件入口完成核心动作，并有与本轮交付范围匹配的真实验证证据。
